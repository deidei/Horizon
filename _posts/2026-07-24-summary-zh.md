## [将计算图编译为 Transformer 权重的编译器，无需训练](https://www.reddit.com/r/MachineLearning/comments/1v5fxbe/i_built_a_compiler_that_turns_computation_graphs/) ⭐️ 9.0/10

新编译器 Torchwright 将 Python 计算图转换为标准 Phi-3 Transformer 的权重，可在原生 HuggingFace 中加载，无需任何训练。该项目已开源，包含 12 个可运行示例。 这项工作能够将任意算法直接编译为标准 Transformer 的权重，推动了机制可解释性和程序合成的发展。它在无需训练的情况下，弥合了人类可读程序与预训练 Transformer 架构之间的鸿沟。 Torchwright 以 Phi-3 架构为目标，生成的检查点可通过`transformers`库加载，无需`trust_remote_code`。与之前的 RASP/Tracr 不同，它使用普通 Python 表达计算图，并为标准模型（而非定制模型）生成权重。

reddit · r/MachineLearning · /u/notforrob · 7月24日 16:15

**背景**: Transformer 是从数据中学习算法的神经网络，但尚不清楚它们架构上能表达哪些算法。RASP 是一种专为表达 Transformer 计算设计的编程语言，Tracr 将 RASP 程序编译为 Transformer 权重，但两者都需要定制架构或训练。Phi-3 是微软最新推出的小型语言模型，性能强大，而 HuggingFace 的 Transformers 库提供了标准实现。

## [Postgres LISTEN/NOTIFY 可扩展至每秒 6 万次，挑战先前观点](https://www.dbos.dev/blog/postgres-listen-notify-scalability) ⭐️ 8.0/10

DBOS 的新基准测试表明，PostgreSQL 的 LISTEN/NOTIFY 每秒可处理 6 万次通知，延迟为毫秒级，这与先前关于全局锁导致吞吐量仅约 2900 次/秒的报告相矛盾。 这挑战了关于 PostgreSQL 可扩展性的普遍看法，可能鼓励更多开发者使用 LISTEN/NOTIFY 构建实时应用，而无需依赖外部消息队列。 该基准测试使用了 96 核、384GB 内存的服务器，并需要代码级优化；在默认设置或较小硬件上可能无法达到相同结果。

hackernews · KraftyOne · 7月24日 19:05 · [社区讨论](https://news.ycombinator.com/item?id=49040296)

**背景**: LISTEN/NOTIFY 是 PostgreSQL 的一项功能，允许数据库会话之间进行异步通知。长期以来，人们认为其扩展性差，因为一个全局独占锁序列化了 NOTIFY 提交，将吞吐量限制在约每秒 2900 次。这篇博客声称通过精心优化克服了这一限制。

## [安全摄像头在登录页面泄露 GitHub 管理员令牌](https://hhh.hn/hanwha-github-token/) ⭐️ 8.0/10

研究发现某款安全摄像头的登录页面中硬编码了一个 GitHub 管理员令牌，暴露出严重的安全疏忽。该漏洞由安全研究人员发现并报告。 此事件凸显了物联网设备中的严重安全漏洞，制造商往往忽视基本的安全实践。这种硬编码的令牌可能导致对公司基础设施和敏感数据的未授权访问。 该令牌是具有完全仓库访问权限的 GitHub 管理员级令牌，直接嵌入在摄像头登录页面的源代码中。研究人员负责任地披露了该问题，但更广泛的影响凸显了物联网需要更好的安全标准。

hackernews · hhh · 7月24日 11:54 · [社区讨论](https://news.ycombinator.com/item?id=49034292)

**背景**: GitHub 管理员令牌是一种凭证，允许在 GitHub 仓库上执行管理操作，如管理分支、绕过保护或访问敏感数据。将此类令牌硬编码在设备固件或 Web 界面中存在重大安全风险，因为一旦令牌暴露，攻击者就可以完全控制相关仓库。物联网设备经常存在不良安全实践，包括默认凭据和硬编码密钥。
